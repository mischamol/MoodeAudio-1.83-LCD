# Siri Remote control for moOde Audio

This guide describes how to reproduce a working Siri Remote setup for moOde Audio on a Raspberry Pi, including discovering the Bluetooth MAC address, pairing the remote, testing the moOde REST API, and installing the daemon.

## Tested environment

- Raspberry Pi 4B, 2 GB
- moOde Audio on Raspberry Pi OS 13.6 Trixie, 64-bit
- Linux 6.18.39
- Apple Siri Remote using Bluetooth LE and HID over GATT
- Tested Apple vendor/product ID: `004C:0266`

The known GATT layout for this remote is:

| Purpose | Handle |
|---|---:|
| HID service | `0x0015` |
| Input-enable value | `0x001d` |
| Input-report value | `0x0023` |
| Input-report CCCD | `0x0024` |

The required initialization sequence is:

1. Write `01 00` to CCCD handle `0x0024` using an ATT Write Request.
2. Write `AF` to value handle `0x001d` using an ATT Write Request.
3. Process notifications received from handle `0x0023`.

Notifications are enabled first so an input report emitted immediately after
the feature-report write cannot be lost. This follows the effective order in
the BlueZ HoG and `siri-remote-lkm` paths: start HID input, then send feature
report `F0 AF`. BlueZ removes report ID `F0` before its ATT write, leaving the
single byte `AF` used above.

## 1. Prepare the Raspberry Pi

Check Python and Bluetooth:

```sh
python3 --version
systemctl status bluetooth
bluetoothctl show
```

Bluetooth should report `Powered: yes`. If it does not:

```sh
sudo systemctl enable --now bluetooth
bluetoothctl power on
```

## 2. Discover the Siri Remote MAC address

Start the interactive Bluetooth tool:

```sh
bluetoothctl
```

Enter these commands at the `bluetoothctl` prompt:

```text
power on
agent NoInputNoOutput
default-agent
scan le
```

Place the Siri Remote close to the Raspberry Pi. Press and hold **Menu** and
**Volume Up** together for approximately five seconds.

A new device should appear, for example:

```text
[NEW] Device 70:48:0F:F2:65:99 Siri Remote
```

In this example, the MAC address is:

```text
70:48:0F:F2:65:99
```

A backslash sometimes shown before a colon in Markdown is only an escape
character; it is not part of the actual MAC address.

If many devices appear, list the discovered devices:

```text
devices
```

Inspect a likely candidate:

```text
info 70:48:0F:F2:65:99
```

For the tested remote, look for information resembling:

```text
Name: Siri Remote
Modalias: bluetooth:v004Cp0266...
UUID: Human Interface Device
```

Relevant identifiers are:

- Apple vendor ID: `004C`
- Product ID: `0266`
- HID service UUID: `00001812-0000-1000-8000-00805f9b34fb`

Do not assume that another Siri Remote has the same MAC address. Always use the
address discovered on the target Raspberry Pi.

## 3. Pair and trust the remote

While still in `bluetoothctl`, enter:

```text
pair 70:48:0F:F2:65:99
trust 70:48:0F:F2:65:99
disconnect 70:48:0F:F2:65:99
scan off
quit
```

Replace the sample MAC address with the address discovered in the previous
step.

Verify the result:

```sh
bluetoothctl info 70:48:0F:F2:65:99
```

The output should include:

```text
Paired: yes
Trusted: yes
```

`Connected: no` is acceptable at this stage. The daemon will establish its own
raw ATT connection.

## 4. Test the moOde REST API

Test Play/Pause directly on the Raspberry Pi:

```sh
curl -G -S -s \
  --data-urlencode 'cmd=toggle_play_pause' \
  http://localhost/command/
```

Test Volume Up:

```sh
curl -G -S -s \
  --data-urlencode 'cmd=set_volume -up 5' \
  http://localhost/command/
```

Test Volume Down:

```sh
curl -G -S -s \
  --data-urlencode 'cmd=set_volume -dn 5' \
  http://localhost/command/
```

Test Previous and Next with local queue items playing:

```sh
curl -G -S -s --data-urlencode 'cmd=previous' http://localhost/command/
curl -G -S -s --data-urlencode 'cmd=next' http://localhost/command/
```

Confirm in the moOde interface that playback, volume, and queue position
actually change.

### External-renderer guard

Ordinary remote commands are ignored while moOde reports an external renderer
as active, including AirPlay, Spotify Connect, Bluetooth, Squeezelite, and the
other renderer flags exposed by `get_cfg_system`. This covers Play/Pause,
Volume, Previous/Next, Menu/Back, and optional ordinary mappings. The
three-second Home shutdown always remains available, as does background battery
monitoring. Pressing a blocked button
shows `Disabled:` plus the active renderer name for one second through the
non-blocking latest-wins overlay. The display names are Bluetooth, AirPlay,
Spotify, Deezer, Squeezelite, Plexamp, RoonBridge, Audio Input, and Multiroom
Receiver; the final name is split across two lines.

The daemon checks the read-only moOde status endpoint only when an ordinary
remote action arrives and caches it for 0.25 seconds. It does not continuously
poll renderer state. A failed status read blocks the ordinary action rather
than risking control of the external stream. Configure this with:

```text
SIRI_IGNORE_DURING_RENDERER=yes
SIRI_RENDERER_CACHE_SECONDS=0.25
```

## 5. Download the software from GitHub

Run the following commands directly on the Raspberry Pi:

```sh
cd ~
git clone --depth 1 https://github.com/mischamol/moOdeAudioProjects.git
cd moOdeAudioProjects/SiriRemote
```

The source is maintained in the
[SiriRemote directory](https://github.com/mischamol/moOdeAudioProjects/tree/main/SiriRemote).

If the repository was cloned previously, update that checkout instead:

```sh
cd ~/moOdeAudioProjects
git pull --ff-only
cd SiriRemote
```

## 6. Install the daemon

From the `SiriRemote` directory on the Raspberry Pi:

```sh
sudo sh ./install.sh 70:48:0F:F2:65:99
```

Replace the sample MAC address if necessary.

The installer creates or updates:

```text
/usr/local/sbin/siri_remote_moode.py
/etc/systemd/system/siri-remote-moode.service
/etc/default/siri-remote-moode
```

It also enables and starts the service.

## 7. Perform the first connection test

Follow the service log:

```sh
journalctl -u siri-remote-moode -f
```

When this appears:

```text
Connecting to Siri Remote 70:48:0F:F2:65:99
```

press a button on the remote to wake it. A successful initialization looks like:

```text
Enabling notifications via 0x0024
Activating input: writing AF to 0x001d
Ready; listening for notifications on 0x0023
```

Button presses should then produce messages such as:

```text
Play/Pause -> toggle_play_pause
Volume + -> set_volume -up 5
Volume - -> set_volume -dn 5
Touchpad left / Previous -> previous
Touchpad right / Next -> next
```

Press `Ctrl+C` to stop following the log. This does not stop the daemon.

## 8. Verify systemd operation

Check the service:

```sh
systemctl status siri-remote-moode
systemctl is-enabled siri-remote-moode
```

The expected state is:

```text
Active: active (running)
enabled
```

Test startup after a reboot:

```sh
sudo reboot
```

After the Pi has restarted:

```sh
journalctl -u siri-remote-moode -f
```

Press a remote button to wake it. The daemon reconnects automatically, using a
backoff between 0.2 and 1 second.

## Button mapping

| Notification | Button | Default moOde command |
|---|---|---|
| `00 00` | Release | None |
| `00 01` short press | TV/Home | None |
| `00 01` held for 3 seconds | TV/Home | Shut down the Raspberry Pi |
| `00 02` | Volume Up | `set_volume -up 5` |
| `00 04` | Volume Down | `set_volume -dn 5` |
| `00 08` | Play/Pause | `toggle_play_pause` |
| `00 10` | Microphone/Siri | Ignored |
| `00 20` | Menu/Back | Alternate Playback and the last Library view |
| Touchpad left + physical click | Previous track | `previous` |
| Touchpad right + physical click | Next track | `next` |

Ordinary touches and swipes are ignored. Only a physical touchpad click invokes
a command. The first-generation X range is approximately `2278..3914`; the
default split is `3096`, with a configurable center dead-zone of 60 units on
either side. Configure this using `SIRI_TOUCH_X_SPLIT`,
`SIRI_TOUCH_DEAD_ZONE`, and `SIRI_TOUCH_MAX_AGE_SECONDS`.

Menu/Back uses Python `ctypes` and the X11 libraries already required by the
local moOde display to alternate between Playback and the last Library view.
The action starts as soon as Menu is pressed. It clicks moOde's cover-art link
rather than artist metadata, because moOde
routes radio and file metadata clicks to different views. The cover link is
source-independent. Before every click, the script reads moOde's persisted
`current_view`, so manual navigation is respected: `playback,album` returns to
Album and `playback,radio` returns to Radio Stations. Folder, Tag, and Playlist
use the same mechanism. At startup the script waits for X11 and first
synchronizes the UI to Playback. It installs no additional package or
configuration file and modifies no moOde WebUI file.

### Non-blocking on-screen feedback

The daemon uses the X11, Cairo, and Lato components already present on moOde to
show a one-second circular overlay. It does not install a compositor or another
package and does not modify moOde files. The anthracite circle uses 60% opacity
and retains 40% of the captured screen, keeping the background clearly visible.
A thin, partially transparent white outline separates it from the cover art.
Regular-weight labels and bold primary values match the visual hierarchy of
the moOde interface. On the tested 720 x 1280 portrait display, the overlay
center is aligned exactly with the cover-art center.

- Play/Pause uses the resulting state returned by `toggle_play_pause`.
- Volume uses the actual percentage returned by `set_volume`.
- Physical touchpad clicks show Previous or Next.
- Home shows an interruptible `3`, `2`, `1` shutdown countdown, followed by
  `Shutdown` and `0`. The final power symbol uses exactly the same size and
  position as the countdown symbol.
- At 5–9%, a white battery overlay shows the freshly read percentage for one
  second every five minutes.
- At 0–4%, that fresh reading is repeated every minute and the white
  battery overlay flashes three times.
- Menu/Back deliberately has no overlay.

Bluetooth input, HTTP commands, and drawing use separate workers. Drawing can
therefore never delay a remote action. The display worker is latest-wins rather
than FIFO: a new button event immediately replaces the current or pending
overlay. Rapid volume clicks do not cause old percentage screens to be replayed
later. After hiding an overlay, the worker briefly allows Chromium to repaint
before another background capture, preventing old overlay content from being
captured underneath the next notification. Configure or disable this feature
in `/etc/default/siri-remote-moode`:

```text
SIRI_OVERLAY=yes
SIRI_OVERLAY_SECONDS=1
```

Battery reads stay inside the single ATT event loop, so no concurrent Bluetooth
operation is introduced. The remote is read once after connecting, every 15
minutes normally, every five minutes at 5–9%, and every minute at 0–4%. Each low
or critical warning therefore displays a freshly read percentage:

```text
SIRI_BATTERY_CHECK_SECONDS=900
SIRI_BATTERY_LOW_CHECK_SECONDS=300
SIRI_BATTERY_CRITICAL_CHECK_SECONDS=60
SIRI_BATTERY_LOW_PERCENT=10
SIRI_BATTERY_CRITICAL_PERCENT=5
```

The overlay has an empty X11 input shape, so Menu/Back clicks pass through it.

Commands can be changed in:

```text
/etc/default/siri-remote-moode
```

Apply configuration changes with:

```sh
sudo systemctl restart siri-remote-moode
```

To inspect the decoded touch coordinate, set `SIRI_DEBUG=yes` in that file,
restart the service, and follow the log:

```sh
sudo systemctl restart siri-remote-moode
journalctl -u siri-remote-moode -f
```

Example:

```text
Touch report: x=3600 split=3096 buttons=0x80 ...
Touchpad right / Next -> next
```

The TV/Home long-press is configured with:

```text
SIRI_HOME_BUTTON_MASK=0x01
SIRI_HOME_HOLD_SECONDS=3
SIRI_HOME_COMMAND=/usr/bin/systemctl poweroff
```

The Home button must remain pressed continuously for three seconds. Releasing
it earlier cancels the shutdown and performs no other action. If another remote reports a different Home code,
enable debug logging, observe its `Input notification`, and update the mask.

The Microphone/Siri button is intentionally ignored. On this first-generation
remote it also starts Apple's voice/audio path, which can reset the raw ATT
connection because this userspace daemon implements HID input but not Apple's
Siri audio protocol. There is deliberately no manual battery-display command on
any button. Automatic low-battery monitoring and its warnings remain active.

## Troubleshooting

### Connection timed out

The remote may be asleep and not advertising. Press a button while the log
shows `Connecting to Siri Remote ...`. The next reconnect attempt may take up
to 30 seconds.

### Device or resource busy

Another process or BlueZ connection is using ATT fixed channel 4. Reset the
connection:

```sh
sudo systemctl stop siri-remote-moode
bluetoothctl disconnect 70:48:0F:F2:65:99
sudo systemctl restart bluetooth
sleep 5
sudo systemctl start siri-remote-moode
```

This temporarily disconnects other Bluetooth devices attached to the Pi.

Check for old test clients:

```sh
pgrep -af 'gatttool|bluepy|siri_remote'
```

### Authentication or authorization errors

Verify the bond and trust state:

```sh
bluetoothctl info 70:48:0F:F2:65:99
```

If necessary:

```sh
bluetoothctl trust 70:48:0F:F2:65:99
sudo systemctl restart siri-remote-moode
```

The default `SIRI_SECURITY=medium` requests an encrypted connection based on
the existing Bluetooth bond.

### Check CPU usage

The fixed daemon uses a blocking Bluetooth socket with explicit `select()`
polling. At idle, CPU usage should be close to zero:

```sh
ps -p "$(systemctl show siri-remote-moode -p MainPID --value)" -o pid,pcpu,cmd
```

## Implementation notes

The daemon uses Linux raw Bluetooth L2CAP/ATT fixed channel 4. It does not
depend on `gatttool`, `bluepy`, `bleak`, `dbus_next`, `dbus`, or `gi`.

The tested remote uses ATT MTU 23. Battery keepalive is disabled because it did
not improve connection reliability. When BlueZ wins the reconnect race and
occupies fixed channel 4, the daemon asks
`bluetoothctl` to disconnect that stale connection and retries automatically.

The `0xAF` initialization was derived from
[SiriRemote-Linux](https://github.com/Yanndroid/SiriRemote-Linux). That project
uses `writeCharacteristic(0x001d, b'\xAF', True)`, where `True` selects a write
with response. The daemon therefore sends ATT Write Requests and verifies the
corresponding ATT Write Responses before it starts listening.

The Gen-1 touch layout and coordinate normalization are based on
[SiriRemote-Linux](https://github.com/Yanndroid/SiriRemote-Linux),
[siri-remote-lkm](https://github.com/Yanndroid/siri-remote-lkm), and
[retsyx/SiriRemote](https://github.com/retsyx/SiriRemote). The current moOde
command endpoint forwards `previous` and `next` to MPD, as shown in the
[official moOde source](https://github.com/moode-player/moode/blob/develop/www/command/index.php).

## Uninstall

Run the included uninstaller from the extracted package directory:

```sh
sudo sh ./uninstall.sh
```

This stops and disables the service and removes the installed daemon, unit file,
and `/etc/default/siri-remote-moode`. To retain the configuration for a later
installation, use:

```sh
sudo sh ./uninstall.sh --keep-config
```

Bluetooth pairing data and separate BlueZ configuration are not changed.

The current `bluetoothctl` command syntax is documented by the
[BlueZ project](https://github.com/bluez/bluez/blob/master/doc/bluetoothctl.rst).
